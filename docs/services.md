# Service documentation

This is **Task 2**: every AWS service in the design, documented in the format the brief asks for – **Service · Role · Why over an alternative · Connects to** – plus a **Configuration** column with the real settings.

| Column | What it answers |
|---|---|
| **Role** | What the service does in this platform |
| **Why over an alternative** | Why it was chosen instead of a named alternative (for example EC2, EBS, DynamoDB, a NAT instance or a REST API) |
| **Connects to** | Which other parts of the design it talks to |
| **Configuration** | How it is set up – every value is taken from the Terraform code in [`infra/`](../infra), and the file is named at the end of the cell |

> **Deployed demo (AWS Free plan):** RDS Proxy, Route 53 and ACM are part of the production design but were not created in the demo account. There the Lambdas connected to RDS directly over verified TLS, and backups were kept 1 day instead of 7. Rows marked *(production only)* show this.

## 1. Edge and frontend

| Service | Role | Why over an alternative | Connects to | Configuration |
|---|---|---|---|---|
| **Amazon Route 53** *(production only)* | DNS for `exams.uni.ac.uk` | Alias records to CloudFront are free and resolve at the zone apex, which a CNAME at the university's DNS provider cannot do. Route 53 also has a 100% availability SLA | CloudFront, ACM (DNS validation) | • A and AAAA alias records to the distribution, plus DNS-validation records for the certificate<br>• Optional: when no domain is set, the CloudFront domain is used<br><sub>Terraform: `edge.tf`</sub> |
| **AWS Certificate Manager (ACM)** *(production only)* | TLS certificate for the custom domain | Free, auto-renewing certificates, compared with buying a certificate and uploading it manually | CloudFront, Route 53 | • Issued in us-east-1 (required by CloudFront) with DNS validation<br>• Viewer TLS ≥ 1.2 (`TLSv1.2_2021`) |
| **Amazon CloudFront** | Single HTTPS entry point: `/*` serves the SPA from S3, `/api/*` goes to API Gateway | Using one origin for the frontend and the API removes CORS and puts WAF in front of both. Edge caching keeps static traffic off the region during the peak. Cheaper and simpler than an ALB with EC2 web servers | Route 53, WAF, S3 frontend, API Gateway | • `PriceClass_100`<br>• Origin Access Control (SigV4) to S3<br>• HTTPS only (redirect)<br>• API behaviour uses `CachingDisabled` and `AllViewerExceptHostHeader` so the `Authorization` header is forwarded<br>• Static behaviour uses `CachingOptimized` with compression<br>• AWS-managed security-headers policy (HSTS, X-Frame-Options)<br><sub>Terraform: `edge.tf`</sub> |
| **AWS WAF** | Blocks common web attacks and floods before they reach the API | Managed rule groups need no rule writing, unlike custom Lambda@Edge filtering. HTTP API cannot attach WAF directly, so WAF goes on CloudFront | CloudFront, CloudWatch | • Scope `CLOUDFRONT` (us-east-1)<br>• Rules: `AWSManagedRulesCommonRuleSet` (with `SizeRestrictions_BODY` set to *count*, because autosave bodies can exceed 8 KB) and `KnownBadInputs`<br>• Rate limit of **20,000 requests per 5 minutes per IP**, set high because a whole campus can share one NAT IP |
| **Amazon S3 (frontend bucket)** | Hosts the static single-page app (HTML/CSS/JS) | No servers to patch or scale, unlike EC2 or ECS hosting a web server. Durability of 11 nines | CloudFront (OAC only) | • All public access blocked<br>• SSE-S3<br>• Bucket policy allows `s3:GetObject` only from this distribution's ARN<br>• `config.js` is generated by Terraform with `no-cache`<br><sub>Terraform: `storage.tf`</sub> |

## 2. Identity and API

| Service | Role | Why over an alternative | Connects to | Configuration |
|---|---|---|---|---|
| **Amazon Cognito** | Role-based sign-in. Groups `students`, `tutors` and `admins` become a `cognito:groups` claim in the JWT | Fully managed and free for the first 10,000 monthly active users, which covers all 8,400 users. It can federate with the university's SAML IdP (Azure AD) later. A custom user table plus password hashing in RDS would mean building and securing that ourselves | Browser, API Gateway (JWT authorizer), admin Lambda | • Username = email<br>• **Admin-create-only** (no self sign-up)<br>• Password at least 10 characters with mixed case and digits<br>• Optional TOTP MFA for staff<br>• ID and access tokens last 4 h (longer than any exam), refresh token 1 day<br>• Public app client (no secret) with `USER_PASSWORD_AUTH`, SRP and refresh flows<br><sub>Terraform: `auth.tf`</sub> |
| **Amazon API Gateway (HTTP API)** | REST endpoints `/api/*`, JWT validation and throttling | About 70% cheaper and lower latency than a REST API, and it has a native JWT authorizer. Compared with an ALB it needs no VPC load balancer to keep running and checks auth before invoking Lambda | CloudFront, Cognito, api and admin Lambdas, CloudWatch Logs | • 19 explicit routes (no `ANY` catch-all)<br>• JWT authorizer with issuer = the user pool and audience = the app client<br>• `/api/health` is public<br>• Stage throttling burst **5,000**, rate **2,000 req/s**<br>• JSON access logs, detailed metrics<br><sub>Terraform: `api.tf`</sub> |

## 3. Compute

| Service | Role | Why over an alternative | Connects to | Configuration |
|---|---|---|---|---|
| **AWS Lambda – api** | Business logic: exams, attempts, autosave, results, assignments, presigned URLs | Scales from 0 to thousands of concurrent executions in seconds with no capacity planning for the exam peak, and costs nothing between exams. EC2 or ECS Auto Scaling takes minutes to add capacity and must run all the time | API Gateway, RDS, Secrets Manager, SQS marking queue (via endpoint), S3 uploads (presign) | • Node.js 22 on **arm64 (Graviton, about 20% cheaper)**, 512 MB, 15 s timeout<br>• **VPC: private app subnets in both AZs**<br>• 1 database connection per instance<br>• One IAM role per function: `secretsmanager:GetSecretValue` on the DB secret only (or `rds-db:connect` with RDS Proxy), `sqs:SendMessage` (marking queue), `s3:PutObject/GetObject` on `assignments/*`, KMS `GenerateDataKey/Decrypt`<br><sub>Terraform: `compute.tf`</sub> |
| **AWS Lambda – admin** | Creates Cognito users, assigns groups, lists users | Kept separate from the api function so only this role holds Cognito admin rights. Runs **outside the VPC** because it only needs the Cognito API, so it needs no NAT | API Gateway, Cognito | • 256 MB, 10 s<br>• IAM: `AdminCreateUser`, `AdminAddUserToGroup` and `ListUsersInGroup` on this pool only |
| **AWS Lambda – marking worker** | Auto-marks MCQs, fans out result emails, and auto-submits expired attempts every minute | Asynchronous, so a slow marking job never delays a student's request. Lambda is cheaper and simpler for bursty background work than an always-on worker on EC2 or Fargate | SQS marking queue, EventBridge, RDS, SQS notify queue | • 512 MB, 60 s, VPC<br>• SQS event source with batch 10 and a 1-second batching window, `ReportBatchItemFailures`, **maximum concurrency 20** (caps database load) |
| **AWS Lambda – upload processor** | Records each S3 upload in the database and queues the tutor email | Event-driven, so the browser does not have to call a "confirm upload" API that could be skipped or faked | SQS uploads queue, S3 (HeadObject via gateway endpoint), RDS, SQS notify queue | • 256 MB, 30 s, VPC<br>• Maximum concurrency 10<br>• Idempotent insert (`s3_key` UNIQUE) |
| **AWS Lambda – notify worker** | Sends emails through SES | Isolates email sending so SES throttling or outages never affect exams. Runs outside the VPC (no NAT needed for SES) | SQS notify queue, SES | • 256 MB, 30 s<br>• **Maximum concurrency 5**, which keeps it under the SES send rate<br>• IAM: `ses:SendEmail` only `From` the configured sender |
| **AWS Lambda – migrate** | Applies `schema.sql` on every deploy | Keeps the database schema reproducible from code without a bastion host or manual `psql` | RDS | • Invoked by Terraform (`aws_lambda_invocation`) whenever the schema or code hash changes<br>• Retries for about 4 minutes while the database becomes reachable |
| **Amazon EventBridge** | Runs the auto-submit job every minute | Managed, serverless scheduling, compared with a cron job on an EC2 instance that is a single point of failure | marking Lambda | • `rate(1 minute)` rule targeting the marking Lambda<br><sub>Terraform: `compute.tf`</sub> |

## 4. Data and storage

| Service | Role | Why over an alternative | Connects to | Configuration |
|---|---|---|---|---|
| **Amazon RDS for PostgreSQL (Multi-AZ)** | System of record: exams, attempts and autosaved answers, marks, assignments, submissions | The data is relational (exams → attempts → marks) and needs transactions and ad-hoc reporting for results and appeals. **Multi-AZ** keeps a synchronous standby in AZ B with automatic failover in 1–2 minutes. DynamoDB would need hand-designed access patterns and makes reporting harder. Aurora is the upgrade path, but its minimum cost is higher for a 400–500-user baseline | Lambda (VPC), RDS Proxy *(production)*, Secrets Manager, KMS, AWS Backup, CloudWatch | • PostgreSQL 16, `db.t4g.micro` for the demo and **`db.m6g.large` for exam week**<br>• `multi_az = true`<br>• **Private data subnets in 2 AZs, `publicly_accessible = false`**, security group allows 5432 only from the Lambda security group (and the RDS Proxy security group in production)<br>• gp3 storage 20 GB autoscaling to 200 GB<br>• **Encrypted with the KMS CMK**<br>• `rds.force_ssl = 1`<br>• **Point-in-time restore** (about 5-minute RPO): 7 days in production, 1 day on the Free plan<br>• Performance Insights<br>• Postgres logs sent to CloudWatch<br><sub>Terraform: `database.tf`</sub> |
| **Amazon RDS Proxy** *(production only – switched on for exam week)* | Connection pooling and faster failover between Lambda and RDS | Without it, 3,000 concurrent Lambdas could open 3,000 connections and exhaust PostgreSQL's `max_connections`. It also redirects connections on failover without waiting for the DNS TTL. Compared with PgBouncer on EC2, there is nothing to run or patch and it is multi-AZ | Lambda (VPC), RDS, Secrets Manager | • `require_tls = true`, **`iam_auth = REQUIRED`** (Lambdas use IAM tokens and no stored password)<br>• Nodes in both data subnets<br>• `max_connections_percent = 90`, idle client timeout 30 minutes<br>• Controlled by `enable_rds_proxy` (`false` on the Free plan) |
| **Amazon S3 (uploads bucket)** | Stores assignment files (PDF/ZIP up to 50 MB) for 5 years | Cheaper and more durable (11 nines across at least 3 AZs) than EBS or EFS. **Presigned POST keeps 50 MB uploads off API Gateway (10 MB limit) and Lambda (6 MB)**. Lifecycle rules handle 5-year retention automatically | Browser (presigned POST/GET), api and upload Lambdas, SQS uploads queue, KMS | • Block all public access<br>• **SSE-KMS with the CMK** and S3 Bucket Key<br>• Versioning on<br>• Bucket policy denies non-TLS requests<br>• CORS allows POST/GET only from the app origin<br>• **Lifecycle: Standard-IA after 30 days → Glacier Instant Retrieval after 180 days → Deep Archive after 365 days → expire after 1,825 days (5 years)**<br>• Noncurrent versions expire after 30 days<br>• Incomplete multipart uploads are aborted after 1 day<br>• `ObjectCreated` events on `assignments/` go to SQS<br><sub>Terraform: `storage.tf`</sub> |
| **AWS Backup** | Long-term database snapshots for 5-year record keeping and restores | One central policy with a vault encrypted by our key, rather than manual snapshot scripts. It also keeps records beyond the 35-day maximum PITR window | RDS, KMS | • Vault encrypted with the CMK<br>• Daily backups kept 35 days<br>• **Monthly backups moved to cold storage after 90 days and kept 1,825 days**<br><sub>Terraform: `backup.tf`</sub> |

## 5. Asynchronous processing and email

| Service | Role | Why over an alternative | Connects to | Configuration |
|---|---|---|---|---|
| **Amazon SQS** (marking, uploads, notify and 3 DLQs) | Buffers background work so peaks and failures don't affect students | Fully managed with at-least-once delivery and built-in retries and DLQs. Simpler and cheaper than running Amazon MQ or Kafka (MSK) for simple work queues. SNS alone would not buffer messages or support retries with back-pressure | S3 (event source), api, marking and upload Lambdas (producers), Lambda event source mappings (consumers) | • SSE-SQS encryption<br>• Long polling of 20 s<br>• Visibility timeout 60–120 s<br>• Retention 4 days (DLQ 14 days)<br>• **Redrive to the DLQ after 5 receives**<br>• The uploads queue policy allows `s3.amazonaws.com` only from this bucket and account<br><sub>Terraform: `queues.tf`</sub> |
| **Amazon SES** | Sends "results released" and "new submission" emails | Pay-per-email ($0.10 per 1,000) and built for application email at volume. SNS email subscriptions cannot send personalised messages to individual addresses. Using a university SMTP relay would need credentials and a NAT gateway | notify Lambda, students, tutors | • Verified sender identity<br>• Test recipients are verified while the account is in the sandbox<br>• Production access is requested before go-live, and SPF, DKIM and DMARC are configured on the university domain<br><sub>Terraform: `monitoring.tf`</sub> |

## 6. Networking

| Service | Role | Why over an alternative | Connects to | Configuration |
|---|---|---|---|---|
| **Amazon VPC** | Network isolation for the database and the Lambdas that use it | Putting the database in a private network is a security requirement, and a public RDS endpoint is not acceptable | All VPC resources | • `10.20.0.0/16` across **2 AZs**, each with **public** (/24), **private app** (/24) and **private data** (/24) subnets<br>• One private route table per AZ<br><sub>Terraform: `network.tf`</sub> |
| **Internet Gateway and NAT Gateways** | Outbound internet for private subnets (e.g. Lambdas reaching Secrets Manager) | NAT Gateway is managed and highly available within its AZ, unlike a self-managed NAT instance. One NAT per AZ means losing one AZ never cuts egress for the other | Public subnets, private route tables | • `nat_gateway_count = 2`, one NAT in each public subnet<br>• It can be set to 0 because Lambdas reach AWS services through VPC endpoints |
| **VPC Endpoints** | Private access from VPC Lambdas to S3 (gateway) and SQS (interface) | Traffic stays on the AWS network with no internet path, and it costs less than routing all AWS API traffic through NAT (the S3 gateway endpoint is free) | Lambda, S3, SQS | • S3 gateway endpoint on both private route tables<br>• SQS interface endpoint in both app subnets with private DNS, security group allows 443 only from the Lambda security group |
| **Security Groups** | Stateful firewall between tiers | Security groups can reference other groups (Lambda → Proxy → RDS), which network ACLs cannot | Lambda, RDS Proxy, RDS, endpoints | • Lambda SG: no inbound; egress 443 plus 5432 within the VPC<br>• RDS SG: 5432 **only from the Lambda SG** (and from the Proxy SG in production)<br>• Proxy SG: 5432 from Lambda SG only<br>• Endpoint SG: 443 from Lambda SG only<br>• Nothing is open to the internet |

## 7. Security, secrets and monitoring

| Service | Role | Why over an alternative | Connects to | Configuration |
|---|---|---|---|---|
| **AWS KMS** | Encryption at rest with a customer-managed key | A CMK gives a key policy we control, CloudTrail audit of every decrypt, and yearly rotation, compared with AWS-owned keys that offer no visibility | RDS, S3 uploads, Secrets Manager, Performance Insights, AWS Backup | • One CMK `alias/exam-platform-prod`, `enable_key_rotation = true`, 7-day deletion window |
| **AWS Secrets Manager** | Stores the RDS master password | RDS-managed secrets rotate automatically, and the password never appears in Terraform, code or environment variables. SSM Parameter Store has no built-in RDS rotation | RDS, VPC Lambdas (or RDS Proxy), KMS | • `manage_master_user_password = true`, encrypted with the CMK<br>• Only the VPC Lambda roles (or the RDS Proxy role in production) can call `GetSecretValue` on this one secret<br>• Lambdas cache it for 5 minutes and never log it |
| **AWS IAM** | Least-privilege permissions for every component, and GitHub OIDC for CI/CD | Short-lived role credentials everywhere, with no long-lived access keys in GitHub or code | All services | • One role per Lambda scoped to specific ARNs<br>• RDS Proxy role<br>• Backup role<br>• GitHub OIDC deploy role trusted only for `repo:<owner>/<repo>` on `main` and pull requests<br><sub>Terraform: `infra/bootstrap`</sub> |
| **Amazon CloudWatch** | Logs, metrics, alarms and an operations dashboard | Native to every service used, with no agents, unlike a self-hosted Prometheus and Grafana stack | Lambda, API Gateway, RDS, SQS, WAF, SNS | • Log retention 90 days<br>• **Alarms:** API 5xx > 10/min, API p95 latency > 1 s, errors for every Lambda, api Lambda throttles > 0, **any DLQ message**, RDS CPU > 80%, free storage < 2 GB<br>• Dashboard covering requests, latency, concurrency, queue depth, RDS and WAF blocks<br><sub>Terraform: `monitoring.tf`</sub> |
| **Amazon SNS** | Delivers alarms and RDS failover events to on-call staff | A simple fan-out channel to email, SMS or Slack (via Chatbot) | CloudWatch alarms, RDS event subscription | • `exam-platform-prod-alarms` topic with an email subscription<br>• RDS event subscription for `failover`, `failure` and `availability` |
| **AWS CloudTrail** | Audit log of every API call (who changed what) | Required for accountability around exam data. Free for management events | S3 trail bucket | • Multi-region trail with log-file validation, stored in a private S3 bucket |

## 8. CI/CD and infrastructure as code

| Service | Role | Why over an alternative | Connects to | Configuration |
|---|---|---|---|---|
| **Terraform** | Defines the entire stack as code | Cloud-agnostic, with a large module ecosystem. `plan` shows reviewers exactly what will change. Compared with clicking in the console, it makes the stack reproducible and gives a full teardown | AWS APIs | • AWS provider ~> 5.80<br>• Remote state in S3 with native lockfile (`use_lockfile`) and encryption<br>• Bootstrap stack creates the state bucket and OIDC role |
| **GitHub Actions** | Pipeline: test → plan (pull request) → apply (push to `main`) | Already where the code lives and free for this usage, with no extra CodePipeline, CodeBuild or CodeCommit resources to manage | GitHub, AWS IAM (OIDC), S3 state, CloudFront | • `deploy.yml` steps: `npm ci && npm test`, `terraform fmt -check`, `validate`, `plan`, then **auto `apply` on main**, a CloudFront invalidation and a `/api/health` smoke test<br>• `destroy.yml` is a manual teardown that requires typing `DESTROY` |
| **Amazon S3 (Terraform state)** | Remote, versioned Terraform state | Shared and locked state, so CI and developers never overwrite each other's changes, unlike local `.tfstate` files | Terraform, GitHub Actions | • Versioned, SSE-S3, public access blocked, S3-native state locking |
